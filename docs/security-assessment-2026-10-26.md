# 脆弱性診断の結果（2026年10月26日・自己診断）

開発者による自己診断です。第三者の専門機関による診断（ペネトレーションテスト）ではありません。

## 範囲と方法
| 対象 | 方法 |
|---|---|
| 依存パッケージ | `npm audit`（本番用・開発用とも） |
| データベースの権限 | 全ての表の RLS の有無、未ログイン（anon）・ログイン済み（authenticated）に付いている権限、所有者権限で動く関数の呼び出し元確認の有無を SQL で全件確認 |
| サーバー側のコード | 管理者キー（サービスロール）を使う全13か所の権限確認、公開 API（Webhook・開封記録・配信停止・稼働確認）の認証、リダイレクト先の検証、HTML の出力、CSV 出力、ファイルのアップロード |
| ブラウザ側の防御 | 応答ヘッダー（クリックジャッキング・コンテンツの種類・HTTPS 強制・読み込み先の制限） |
| 秘密情報 | Git の全履歴に API キー・パスワードが含まれていないか（値の照合と鍵の書式による検索） |

## 見つかった問題と対応
| # | 重要度 | 内容 | 対応 |
|---|---|---|---|
| 1 | 中（開発環境のみ） | テストツール vitest 3.x に任意のファイルを読める脆弱性（本番の配信物には含まれない） | 4.1.11 以降に更新。`npm audit` は 0 件 |
| 2 | 低 | 内部用の関数 `usage_in_use` を、ログイン済みなら誰でも呼べた。他の組織の ID を知っていれば、その組織の写真の解析枚数・保存容量が分かった（個人情報は含まない） | 利用者から呼べないようにした（他の内部関数2つも同様） |
| 3 | 低（多層防御） | 未ログインの利用者に、表・関数の権限が既定のまま付いていた。行単位の制御（RLS）で中身は読めなかった | 権限そのものを外した。今後作る表・関数にも付かない設定にした |
| 4 | 低 | 写真のアップロード完了の処理が、共通の権限判定ではなく所属の有無だけを見ていた（停止中の組織の条件が抜けていた。二段階認証の必須は直後の処理で止まっていた） | 共通の権限判定に置き換えた |
| 5 | 低 | グラフの CSV 出力で、タグ名などが `=` で始まると表計算ソフトで数式として実行されうる（人物の一括出力は対策済みだった） | 一括出力と同じ処理で無害化した |
| 6 | 低（多層防御） | 読み込み先の制限（Content-Security-Policy）と HTTPS の強制（HSTS）のヘッダーがなかった | 追加。外部のスクリプトや外部サイトへのデータ送信をブラウザが止める |

修正の確認：自動テスト 186 件（追加：未ログインでの全表・関数の拒否、他組織の利用量、CSV の無害化）。本番相当のビルドで画面・写真・二段階認証の登録が新しいヘッダーの下で動くことを確認。

## 問題がなかった項目
- 全ての表で RLS が有効。組織をまたいだ読み書きは自動テストで毎回確認
- 管理者キーを使う処理は、すべて事前に権限を確認しているか、署名・トークンで送り手を確認している
- Webhook（Stripe・Typeform・Tally・汎用）は署名または秘密で認証。秘密は暗号化またはハッシュで保存
- ログイン後の戻り先は自サイト内のパスだけを許可（外部サイトへの誘導を防止）
- メール本文は HTML として無害化してから送信。画面は React の自動エスケープ（`dangerouslySetInnerHTML` 不使用）
- 写真は形式（JPEG・PNG・WebP）と容量（15MB）をストレージ側でも制限し、サーバーで実ファイルを検査
- フォームの送信元の確認（CSRF）は Next.js の Server Actions の仕組みで行われる
- Git の履歴に API キー・パスワードは含まれていない

## 残っている課題（今回は未対応）
- 第三者による脆弱性診断
- 公開の受け口（Webhook・開封記録）の回数制限（現在は送信元の署名確認と本文の大きさの上限のみ）
- 読み込み先の制限で `'unsafe-inline'` を許している（Next.js の仕組み上。nonce 方式への切り替えで強化できる）
- 漏えい済みパスワードの照合・一定時間操作がないときの自動ログアウト（Supabase の有料プランの機能）
