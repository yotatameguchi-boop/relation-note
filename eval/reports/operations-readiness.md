# 運用準備の試験結果（負荷試験・バックアップからの復元試験・監視）

実施日：2026年10月23日　対象：コミット 8793c98 以降

## 1. 負荷試験

### 方法
- `scripts/loadtest.mjs`：ログイン済みのスタッフとして主要な10画面を、実際の利用に近い比率で同時に開き続ける（画面の見出しが出たものだけ成功と数える）。
- 手元：本番ビルド（`next start`）＋手元の Supabase。1組織に上位プランの上限いっぱいのデータを入れた（`scripts/loadtest-setup.mjs`）。
  人物 100,000／連絡先 約150,000／タグ付け 約250,000／イベント 1,000／参加 400,000／企業 5,000／やりとり 200,000／タスク 20,000／操作履歴 100,000
- 本番：https://relationnote.vercel.app（Vercel 東京＋Supabase 東京・無料枠）、デモ組織（人物12件）。

### 見つかった問題と修正
大規模データで、次の3点が目標（95%が2秒以内）を大きく超えていた。いずれも修正済み（結果は変わらないことを既存テストで確認）。

| 問題 | 原因 | 修正前 | 修正後 |
|---|---|---|---|
| 人物一覧・ダッシュボードが遅い | RLS の所属確認（`is_member`/`has_role`）が**行ごと**に実行されていた | 人物一覧 6.8秒、ダッシュボード集計 41秒 | 0.09秒、0.18秒 |
| 人物検索・企業検索が遅い | 連絡先の照合が人物1人ごとの副問い合わせ／企業の集計を全社分計算 | 人物検索 19秒、企業一覧 1.4秒 | 0.19秒、0.02秒 |
| 大きな組織への取り込みが遅い | 登録上限の確認で、1行追加するたびに全件を数えていた | 2,000行の追加 6.1秒（人数に比例して悪化） | 0.05秒 |

（修正前後の時間は、同じデータに対する単独実行の DB 処理時間）

修正内容：`supabase/migrations/20261025000002_rls_performance.sql`（所属組織の一覧を1回だけ求める `my_org_ids()` に置換、84ポリシー）、`…000003_search_performance.sql`、`…000004_people_counter.sql`（組織ごとの人数カウンターと文単位の上限確認）。

### 評価
- **目標（同時10人で95%が2秒以内）は、10万人の組織でも満たした。** どの段階でも失敗（エラー・タイムアウト）は0件。
- 手元では同時20人前後で処理量が頭打ちになった（約12件/秒）。このときデータベースが CPU を使い切っており、ボトルネックは DB。1組織で同時20人が画面を開き続ける状況は、標準プラン（スタッフ10人まで）では起きにくい。
- 本番の Supabase は無料枠（共有 CPU・メモリ 0.5GB）で、手元より非力。**10万人規模の組織を受け入れる前に、Supabase の有料プラン（Small 以上）で同じ試験をやり直す**こと。本番に大量の試験データは入れていない。
- 最も重いのは「重複候補」（同時10人で95% 3.2秒、同姓同名が多い試験データのため組み合わせが約18万組）。実データで遅い場合は、候補の事前計算を検討する。

### 再実行の手順
```
node scripts/loadtest-setup.mjs            # 手元に試験用の組織とデータを作る（初回のみ、約50秒）
npm run build && npx next start -p 3090
BASE=http://localhost:3090 node scripts/loadtest.mjs 1,5,10,20,30 60 > eval/reports/loadtest-local-after.json
```

## 2. バックアップからの復元試験

### 方法
- `scripts/backup.sh`：本番の DB（ロール・スキーマ・データ）と Storage（写真・出力ファイル）を手元に保存し、件数と SHA-256 を記録（`manifest.txt`）。保存先はリポジトリの外（`~/Claude/npo-crm-backups`、本人のみ読める権限）。
- `scripts/restore-test.sh`：**本番と同じ版**の Postgres・Auth・Storage で空の Supabase を別に立て、バックアップを流し込み、次を確認する。
  1. 主要な表の件数がバックアップ時と一致する
  2. すべての表で RLS が有効
  3. Storage のファイルを戻し、全件のハッシュが一致する
  4. 元のアカウントのパスワードでログインでき、RLS 越しに自組織のデータとダッシュボード集計が読める

### 結果
| バックアップ | 大きさ | 取得 | 復元（DB） | 復元（ファイル） | 合計 | 結果 |
|---|---|---|---|---|---|---|
| 本番（デモ）2026-10-23 08:59 | 492KB（ファイル2件） | 15秒 | 1秒 | 1秒未満 | 28秒 | 件数・ハッシュ・ログイン すべて一致 |
| 手元（10万人の組織を含む） | 322MB（ファイル329件） | 16秒 | 19秒 | 5秒 | 51秒 | 件数（参加40万件ほか）・ハッシュ・ログイン すべて一致 |

（合計には復元先の起動 約26秒を含む）

### 試験で分かったこと（手順書に反映済み）
- **Vault の秘密は復元されない**（暗号鍵がプロジェクトごとに違う）。復元後に、ワーカーの呼び出し設定（Vault の `project_url` と `worker_secret`。README「本番に向けて人が行う作業」3）と、外部連携の秘密（Google の再連携・Typeform/Tally の秘密の再発行）をやり直す必要がある。
- **pg_cron の予定は復元されない**。`supabase/migrations` の `cron.schedule(...)` を流し直す。
- ジョブのキュー（pgmq）の表はスキーマのバックアップに含まれない。復元時に `pgmq.create('jobs')` を先に実行する（スクリプトで対応済み）。
- マイグレーションの適用履歴は含まれない。新しいプロジェクトに復元した後は `supabase migration repair --status applied <版>` で履歴を揃える。
- 手元の Auth が本番より古い版だと表の形が合わず失敗する。復元先は本番と同じ版で立てる（スクリプトで対応済み）。

### 運用上の目安
- 復旧目標時間（RTO）：手順に慣れていれば、DB とファイルの復元自体は10万人規模でも1分程度。新しいプロジェクトの作成・秘密の再設定・Vercel の接続先切り替えを含めて **1〜2時間**。
- 復旧時点（RPO）：手動バックアップの間隔に依存。**無料枠には自動バックアップがない**ため、有料化（Pro：毎日の自動バックアップ、PITR は追加契約）までは `scripts/backup.sh` を毎日実行する運用を推奨。

## 3. 監視

| 仕組み | 内容 | 確認結果 |
|---|---|---|
| `/api/health` | 認証なしは状態だけ（ok／degraded／down）。`HEALTH_TOKEN` 付きで各指標としきい値を超えた項目を返す。DB に届かないときは 503 | 本番で ok（DB 応答 31ms） |
| ワーカーの稼働記録 | `process-jobs` が1回動くごとに `worker_heartbeats` に記録。10分以上記録がなければ異常 | 本番で毎分記録されている |
| `ops_health()` | キューの滞留、24時間の失敗ジョブ、止まったジョブ、cron の失敗、メール送信の失敗、DB 容量（400MB で警告。無料枠の上限は500MB） | 本番で全項目 0 |
| GitHub Actions `monitor` | 30分ごとに `/api/health` とログイン画面を確認。異常なら Issue を作成（GitHub からメール通知）、回復したら自動で閉じる | 正常時：成功。異常の模擬（手動実行の `simulate_failure`）で Issue #1 が作成され、次の正常実行で自動で閉じた |

### 監視が拾わないもの
- 個々の組織の連携エラー（Google の再連携が必要など）は、その組織の画面で知らせる。監視の対象外。
- Supabase・Vercel 自体の障害は各社のステータスページを参照（status.supabase.com、vercel-status.com）。
- Actions の定期実行は GitHub の都合で数分〜十数分遅れることがある。より細かい監視が必要なら、外部の死活監視サービスから `/api/health` を呼ぶ。
